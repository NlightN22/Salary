# Salary Web

Web-часть проекта для загрузки отчетов, проверки комплектности, расчета зарплат,
ручных корректировок, генерации PDF и интеграции через API.

Первичный расчетный код остается в основном проекте. Web-сервис использует это
расчетное ядро, но добавляет интерфейс, базу данных, пользователей, права и API.

## Запуск

Из корня проекта:

```bash
./venv/bin/python -m uvicorn salary_web.app:app --reload
```

После запуска:

```text
http://127.0.0.1:8000
```

## Автоматические тесты

Тестовые зависимости устанавливаются отдельно от рабочего контейнера:

```bash
./venv/bin/python -m pip install -r requirements-dev.txt
```

Полный запуск одновременно проверяет тесты и обязательный порог покрытия 100%:

Предупреждения также считаются ошибками: запуск должен проходить без них.

```bash
./venv/bin/python -m pytest
```

Отдельная подробная проверка покрытия:

```bash
./venv/bin/python -m pytest --cov-report=term-missing
```

Тесты используют временные SQLite и каталоги. Рабочая база и существующие
периоды не изменяются. Если покрытие рабочего кода с учетом ветвлений становится
ниже 100%, запуск завершается ошибкой. Проверяются корректные сценарии и отказы: неполный набор
отчетов, пустые и поврежденные Excel, неверная структура, Unicode, повторная
загрузка, права API, пересчет, ручные записи, итоговые суммы и путь PDF.

Если порт или адрес изменится, страница документации API будет показывать
примеры с текущим адресом сервера.

## Первый вход

При первом запуске автоматически создается:

```text
логин:  admin
пароль: значение SALARY_ADMIN_PASSWORD
```

До первого запуска задайте `SALARY_ADMIN_PASSWORD` (не менее 12 символов).
Администратор создается только в базе без пользователей. Переименование или
удаление администратора не восстанавливает стандартную учетную запись.
Для существующей базы переменная не меняет сохраненные пароли.

Сессия действует 12 часов. Смена пароля отзывает предыдущие сессии пользователя.
После обновления формата сессий потребуется повторный вход.
Суммы ручных записей должны быть конечными числами в диапазоне ±1 000 000 000 000;
некорректные значения отклоняются с кодом 422 без изменения расчета.

## Основной сценарий работы

1. Войти в систему.
2. Создать период: направление, год, месяц.
3. Загрузить исходные отчеты.
4. Проверить комплектность и читаемость отчетов.
5. Создать расчеты.
6. Проверить расчет сотрудника в web-интерфейсе.
7. Добавить корректировки, дополнительные выплаты и комментарии.
8. Сформировать PDF.
9. Скачать PDF.

Кнопка расчета активируется только после успешной проверки обязательных отчетов.

## Хранение данных

По умолчанию используется SQLite:

```text
salary_web/service_data/salary.db
```

Исходные Excel и итоговые PDF хранятся вместе в папке подразделения и периода:

```text
data/<название подразделения>/<год>/<номер месяца>/reports/
```

Созданные PDF лежат непосредственно в папке месяца рядом с подпапкой `reports/`.

Имена новых файлов включают полное ФИО, месяц и год:
`Иванов_Иван_Иванович_октябрь_2026.pdf`.
Например: `data/B2B-направление/2026/8/`. Исходные файлы находятся в `reports/`,
а PDF — рядом с этой папкой. Данные расчётов и ручные записи хранятся в SQLite.
Пути существующих файлов перенесены в эту структуру, а записи SQLite обновлены.

В строке каждого сотрудника доступна кнопка «Удалить расчет» с подтверждением.
Она удаляет только этот расчет, его ручные записи и связанный PDF, не исходные отчеты.
Кнопка «Удалить все расчеты» остается. Автоматический расчет можно заново создать из отчетов.

### Ручной расчет

На странице периода раскройте «Создать ручной расчет» и укажите ФИО.
Исходные отчеты не требуются. Добавляйте строки «Название выплаты — сумма —
комментарий». Строки можно редактировать и удалять; итог равен сумме выплат.
Отрицательная сумма означает удержание. PDF содержит те же три колонки и итог.
Для одного сотрудника в одном периоде отдела допускается только один расчет:
автоматический или ручной. Пересчет и замена отчетов не стирают ручной расчет.
«Удалить все расчеты» удаляет и ручные. Прежние расчеты сотрудников, отсутствующих
в новых исходных данных, сохраняются при пересчете.

Веб-страницы периодов разделены по отделам:
`/<название отдела>/<год>/<месяц>`, например `/B2B-направление/2026/08`.
Название берется из админки, пробелы и специальные символы заменяются на `_`.
Устаревшие веб-адреса с ID и API без подразделения удалены; перенаправлений нет.
Названия отделов для веб-адресов должны отличаться. После переименования отдела
короткая ссылка меняется; новая доступна на странице выбора периода.
«Создать расчет» в строке сотрудника пересчитывает только его данные из отчетов,
удаляя его ручные корректировки и выплаты после подтверждения. Расчеты остальных
сотрудников не меняются. Если сотрудника нет в отчетах, прежний расчет сохраняется.
Для полностью ручной расчетки кнопка обновляет итог и открывает заполнение без удаления записей.
Одинаковый месяц в разных отделах открывается отдельно. Подразделение обязательно.

В базе хранятся:

- пользователи;
- направления;
- права пользователей;
- API-ключи и их хэши для проверки;
- периоды;
- загруженные отчеты;
- сотрудники;
- расчетные JSON-снимки;
- дополнительные выплаты;
- корректировки;
- пути к PDF.

Web-версия не создает отдельные JSON-файлы. Расчетный снимок хранится в поле
`calculations.snapshot_json` SQLite и служит источником для страницы расчета и
PDF. Отдельных JSON-файлов в рабочем процессе нет.

Пути отчетов и PDF сохраняются в БД относительно корневого `data/`.
Один набор данных используется локально и в Docker.

## SQLite и PostgreSQL

По умолчанию достаточно SQLite. Для одного-двух пользователей и последовательной
работы с расчетами этого нормально.

Подключение к БД задается переменной окружения:

```bash
DATABASE_URL="sqlite:////path/to/salary.db"
```

Для PostgreSQL можно использовать:

```bash
DATABASE_URL="postgresql+psycopg://user:password@localhost:5432/salary"
```

При переходе на PostgreSQL нужно будет:

1. добавить драйвер PostgreSQL в зависимости;
2. создать базу и пользователя;
3. задать `DATABASE_URL`;
4. перенести данные из SQLite, если они нужны;
5. нормально оформить миграции схемы через Alembic.

Текущий код создает таблицы через SQLAlchemy и содержит легкие SQLite-миграции
для этапа разработки. Для промышленного PostgreSQL лучше добавить полноценные
миграции, чтобы база не развивалась методом «а давайте руками поправим колонку».

Важное ограничение существующей SQLite-базы: если база была создана до
добавления направлений, уникальность периода могла остаться старой — только
`год + месяц`. В новой схеме уникальность правильная: `направление + год +
месяц`. Автоматическая перестройка этой части отключена, чтобы не ломать
существующие связи в SQLite.

## Направления и права

Сервис рассчитан на работу с несколькими направлениями.

Сейчас основное направление:

```text
code: b2b
name: B2B-направление
```

Пользователь видит только те периоды и расчеты, к направлениям которых у него
есть доступ. Администратор видит все.

На странице выбора периода направление выбирается первым. Если у пользователя
несколько направлений, по умолчанию подставляется направление последнего периода,
по которому уже создавались расчеты. Если таких периодов нет — первое доступное
направление.

## Админка

Админка доступна администраторам:

```text
http://127.0.0.1:8000/admin
```

В админке можно:

- создавать направления;
- создавать пользователей;
- менять логин и ФИО пользователя;
- менять пароль пользователя;
- выдавать и убирать права по направлениям;
- назначать и убирать роль администратора;
- активировать и деактивировать пользователя;
- удалять пользователей;
- создавать API-ключи;
- менять название, активность и права API-ключа;
- удалять API-ключи.

Защита от очевидных аварий:

- администратор не может удалить сам себя;
- администратор не может снять с себя права администратора;
- новые API-ключи видны только администраторам;
- старые ключи, созданные до хранения полного ключа, нужно пересоздать.

## Периоды

Период определяется тройкой:

```text
направление + год + месяц
```

Пример:

```text
B2B-направление, 2026, июнь
```

Администратор может удалить период. При удалении удаляются:

- запись периода в базе;
- загруженные отчеты;
- расчеты;
- дополнительные выплаты;
- корректировки;
- созданные PDF;
- связанные файлы web-версии.

Исходные Excel и итоговые PDF периода удаляются вместе с его папкой.

## Исходные отчеты web-версии

Обязательные типы отчетов:

| Код | Название | Подсказка по имени |
| --- | --- | --- |
| `profit` | Отчет по прибыли | `profit.xls` или `profit.xlsx` |
| `brand_sales` | Отчет по продажам брендов / KPI | `brand_sales.xlsx` |
| `debt` | Отчет по дебиторской задолженности | `debt.xlsx` |
| `timesheet` | Табель рабочего времени | файл с названием `Табель` |
| `cycle` | Отчет по циклу сделки | название содержит `цикл` |
| `communications` | Отчет по коммуникациям | название содержит `коммуникации` |

В интерфейсе можно загрузить сразу несколько файлов. Лишние файлы должны
игнорироваться, если сервис не может отнести их к ожидаемым типам отчетов.

Если отчет заменяется, расчеты периода удаляются и должны быть созданы заново.
Это правильно: старый расчет на новых исходниках — это не расчет, а фольклор.

## Ручные записи в расчете

На странице расчета можно добавлять:

- дополнительные выплаты;
- корректировки по разделам;
- комментарии к клиентам с ПДЗ `100 000` и более.

Дополнительные выплаты и корректировки попадают в конец расчета и учитываются
в итоговой таблице web-расчета и PDF.

При добавлении новой записи показывается сообщение:

```text
Запись сохранена и добавлена в конец расчёта
```

При удалении или пересохранении записи это сообщение не показывается.

## PDF

PDF можно создать:

- по одному расчету;
- сразу по всем расчетам периода.

Кнопки в интерфейсе:

- `Создать расчет в PDF`;
- `Скачать PDF`;
- `Создать все расчеты`;
- `Удалить все расчеты`.

Создание PDF периода заново пересчитывает расчеты на основании загруженных
отчетов.


Ссылка на API есть в шапке интерфейса.

## API-ключи

Вход в браузере не заменяет API-ключ. Без ключа, с неверным или выключенным ключом
API отвечает `401` и `{"detail":"Требуется API-ключ"}`. При отсутствии доступа к
подразделению — `403` и `{"detail":"Нет доступа к подразделению"}`.

Для внешних систем используется заголовок:

```text
X-API-Key: sk_salary_...
```

API-ключ создается в админке и привязывается к одному или нескольким
направлениям. Если ключ не имеет доступа к направлению, API вернет ошибку `403`.
Новые ключи сохраняются в базе и доступны администраторам в списке API-ключей.
Для старых ключей, созданных до этого изменения, открытый текст восстановить нельзя.

Для интеграций с 1С/CRM нужно использовать маршруты с кодом направления:

```text
/api/departments/{department_code}/periods/{year}/{month}/...
```

Пример:

```text
department_code = b2b
year = 2026
month = 6
```

Это означает:

```text
B2B-направление, июнь 2026 года
```

## Основные API-команды

### Как выполнить примеры впервые

1. Получите у администратора ключ с доступом к нужному подразделению и его код (`b2b`, например).
2. На macOS откройте «Терминал» через Cmd + Пробел. На Linux откройте терминал.
   В Windows используйте PowerShell: замените `curl` на `curl.exe`, объедините строки
   команды в одну и удалите завершающие строки символы `\`.
3. Замените `sk_salary_...` на полный ключ, `b2b` на код подразделения, `2026/6`
   на нужные год и месяц. Название отдела из веб-адреса не заменяет код API.
4. Сначала выполните только проверку `/api/health`. Не загружайте файлы в рабочий
   период ради проверки связи. Выполняйте дальнейшие команды по одной, проверяя ответы.
5. После `-F` укажите `"file=@/полный путь/к файлу.xlsx"`. Кавычки обязательны для
   путей с пробелами. `file=@profit.xlsx` ищет файл в текущей папке терминала.
6. Возьмите ID нужного сотрудника из ответа сервера, а не подставляйте `1` наугад.
   К относительному `api_download_url` добавьте адрес сервера; ключ нужен и при скачивании.
7. `--output calculation.pdf` сохраняет PDF в текущую папку. На macOS/Linux узнать её
   можно командой `pwd`, проверить файл — `ls -l calculation.pdf`; на macOS открыть папку — `open .`.
   В PowerShell: `Get-Location`, затем `Get-Item calculation.pdf`.

Кнопки копирования и примеры с текущим адресом сервера находятся на `/api-docs`.
Если запрос выполняется с другого компьютера, замените `127.0.0.1` на сетевой адрес
сервера, предоставленный администратором. Ключ не публикуйте: он может сохраняться
в истории терминала. При утечке отключите его и создайте новый.

### Какие действия меняют уже введённые данные

- Загрузка или замена отчёта удаляет автоматические расчёты периода, их ручные
  корректировки, дополнительные выплаты и PDF. Полностью ручные расчётки сохраняются.
- `/calculate` и общий `/pdf` пересчитывают автоматические расчёты и удаляют ручные
  корректировки и дополнительные выплаты у заново рассчитанных сотрудников.
  Полностью ручные расчётки и прежние расчёты сотрудников, отсутствующих в исходниках, сохраняются.
- `/calculations/{calculation_id}/pdf` создаёт PDF из уже сохранённого расчёта,
  сохраняя его корректировки. `/pdf/download` только скачивает файл.
- Ответ `200` на загрузку означает, что файл принят, но не гарантирует правильность
  его содержимого. После загрузки всех файлов выполните `/validate` и проверьте
  `validated`, `missing` и `errors`. Если `validated` не равно `true`, не запускайте расчёт.

### Загрузить отчет

```bash
curl -X POST http://127.0.0.1:8000/api/departments/b2b/periods/2026/6/reports/profit \
  -H "X-API-Key: sk_salary_..." \
  -F "file=@profit.xls"
```

Где `profit` — тип отчета. Другие варианты:

```text
brand_sales
debt
timesheet
cycle
communications
```

### Проверить комплектность


### Получить список расчетов периода

```bash
curl -X GET http://127.0.0.1:8000/api/departments/b2b/periods/2026/6/calculations \
  -H "X-API-Key: sk_salary_..."
```

Пример ответа:

```json
{
  "period_id": 1,
  "department_code": "b2b",
  "year": 2026,
  "month": 6,
  "calculations": [
    {
      "id": 1,
      "employee": "ФИО",
      "status": "calculated",
      "has_snapshot": true,
      "has_pdf": true,
      "data_url": "/api/departments/b2b/periods/2026/6/calculations/1",
      "api_pdf_url": "/api/departments/b2b/periods/2026/6/calculations/1/pdf",
      "api_download_url": "/api/departments/b2b/periods/2026/6/calculations/1/pdf/download"
    }
  ]
}
```

Здесь `id` — внутренний ID расчета в базе. Это не «первый сотрудник июня» и не
номер строки. Поэтому безопасный сценарий такой:

1. получить список расчетов периода;
2. найти нужного сотрудника по полю `employee`;
3. взять его `id`;
4. использовать этот `id` в дальнейших запросах.

### Получить данные одного расчета

```bash
curl -X GET http://127.0.0.1:8000/api/departments/b2b/periods/2026/6/calculations/1 \
  -H "X-API-Key: sk_salary_..."
```

Если подставить `calculations/2`, сервис будет искать расчет с внутренним ID
`2` именно в периоде `b2b / 2026 / 6`. Если такого расчета в этом периоде нет,
вернется `404`.

## Связь web-версии с первичным проектом

Web-сервис не дублирует расчетные формулы. Он вызывает расчетное ядро:

```text
directions/b2b/manager_salary.py
directions/b2b/chief_salary.py
generators/pdf_generator.py
generators/chief_pdf_generator.py
```

Это важно: если меняется формула B2B, менять ее нужно в расчетном ядре, а не
отдельно в web-интерфейсе.

## Что учитывать при развитии

Для истории, графиков и статистики можно постепенно переносить ключевые
расчетные показатели из снимков в отдельные таблицы БД:

- период;
- направление;
- сотрудник;
- тип KPI;
- план;
- факт;
- процент выполнения;
- сумма бонуса;
- ручные корректировки;
- итог.

Снимок расчета в SQLite позволяет сохранить исходный результат и восстановить
PDF за конкретный месяц. Отдельные файлы JSON при этом не создаются.

### Что сохраняется вне контейнера

В `docker-compose.yml` подключены папки:

```text
./salary_web/service_data -> /app/salary_web/service_data
./data                    -> /app/data
```

Это значит, что SQLite-база, загруженные отчеты, созданные PDF и файлы
первичного проекта не пропадут при пересоздании контейнера.

Внутри `/app/data` исходные Excel и PDF разложены по подразделению, году и
месяцу. Excel хранятся в подпапке `reports/`, а PDF — рядом с ней.

База данных web-сервиса остается общей для учетных записей и подразделений.
Расчеты и загруженные отчеты связываются с периодом конкретного подразделения,
а API и web-доступ проверяют права на это подразделение.

### Переменные окружения

Основные переменные:

```text
PORT=8000
DATABASE_URL=sqlite:////app/salary_web/service_data/salary.db
SALARY_SESSION_SECRET=<случайный секрет длиной не менее 32 символов>
SALARY_ADMIN_PASSWORD=<пароль первого администратора длиной не менее 12 символов>
```

`SALARY_SESSION_SECRET` обязателен в Docker. Пустые и стандартные значения
отклоняются. Сгенерировать: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
Сохраните секрет в `.env`; смена секрета завершает старые сессии.
Без заданного секрета локальный запуск использует временный случайный секрет.
`PORT` задает внешний порт, внутри контейнера всегда используется 8000.

При повторной загрузке табеля с тем же именем заменяется предыдущая версия.
Файлы сначала записываются во временный файл, затем получают уникальный путь.
Обрыв загрузки или откат транзакции БД не перезаписывает предыдущий исходник.
Прежние файлы сохраняются на диске; автоматическая очистка архивных файлов пока не выполняется.
Разные имена позволяют загрузить несколько табелей; повтор сотрудника вызывает
ошибку проверки. После правки расчета PDF нужно сформировать повторно:
скачивание старого файла отключается. Для интеграций используйте маршруты
`/api/departments/{department_code}/...` с API-ключом.
